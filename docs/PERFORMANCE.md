# Производительность и качество

Цель: приблизиться к отзывчивости Windows mstsc на одинаковых сервере,
сети, разрешении и содержимом экрана. Это критерий разработки, пока не
подтверждённый результат. Основные серверы: Windows 10/11 Pro, Windows Server
RDS и Linux xrdp-egfx. Клиенты: Cinnamon X11, GNOME и KDE под X11/Wayland.

## Что выяснили

На машине разработки FreeRDP 3.32.2 собрана с WITH_GFX_H264=OFF,
WITH_VIDEO_FFMPEG=OFF, WITH_OPENH264=OFF, WITH_FFMPEG_HWACCEL=OFF.
SIMD включён. Следовательно, аппаратный H.264 здесь сейчас недоступен.
Проверять именно загруженную библиотеку можно без GUI:

    cargo run --locked -- --diagnostics

Возможность сборки, наличие GPU и фактически работающий аппаратный декодер —
три разных проверки. Вывод диагностики пока сообщает только возможности сборки.
Системную FreeRDP автоматически не заменять. Следующая сборка с кодеками должна
устанавливаться отдельно от системной и быть воспроизводимой.

## Практические решения

1. Штатный EGFX/RDPGFX FreeRDP и согласование кодеков с сервером. H.264/AVC444
   объявлять только когда библиотека поддерживает декодирование; сохранить GDI
   для серверов без EGFX. AVC444 рассматривать для чёткого текста, AVC420 для
   сравнения нагрузки/полосы. Не обещать, что один режим быстрее на каждом GPU.
2. Подготовить FreeRDP с WITH_FFMPEG=ON, WITH_VIDEO_FFMPEG=ON,
   WITH_FFMPEG_HWACCEL=ON; проверить итоговую конфигурацию и реальный декодер.
   В FreeRDP 3.32.2 аппаратный путь экспериментальный. Начать с VA-API на
   Intel/AMD; NVIDIA проверять отдельно с доступным FFmpeg backend/драйвером.
   При отказе аппаратного пути нужен программный резервный режим.
3. Уменьшить стоимость вывода: объединять мелкие обновления, не создавать
   неограниченную очередь, сохранять последний законченный кадр. Уже сделано:
   backpressure, учёт frame markers, синхронизация EGFX, передача на EndFrame
   и показ по GTK frame clock. Отладка реального режима описана в NATIVE-RDP.md.
   Далее: dirty rectangles, повторное использование буферов, привязка вывода
   к GTK frame clock. Замерить стоимость каждой стадии до нового усложнения.
4. После стабильного аппаратного декодирования исследовать GPU presentation
   без выгрузки/повторной загрузки полного RGB-кадра: EGL/GL и DMA-BUF.
   GTK 4.14 имеет DmabufTextureBuilder, но текущий GDI API выдаёт CPU framebuffer.
   Zero-copy потребует отдельного пути декодированных поверхностей, контроля
   времени жизни, синхронизации и резервного MemoryTexture. Сейчас его нет.
5. Ввод и курсор обрабатывать независимо от частоты показа кадров. Добавить
   формы аппаратного/локального курсора вместо постоянной стрелки. Отключать
   обработку кадров скрытых вкладок через согласованный suppress-output,
   сохраняя корректное восстановление. Не задерживать обработку протокола
   искусственным sleep ради ограничения FPS.
6. Автоматический режим качества и отдельные пресеты «Текст», «Динамика»,
   «Медленная сеть» — после измерений. Сначала согласование доступных кодеков,
   затем адаптация к сети; не ухудшать шрифты/цветность по умолчанию.
7. Статистика сеанса: negotiated EGFX/codec, фактический software/hardware
   decoder, renderer, FPS при изменениях экрана, copied MB/s, decode/copy/upload
   time, длина очереди ввода, RTT при наличии корректного источника. Сборка
   с HWACCEL=ON не должна отображаться как «GPU используется» без подтверждения.

## Как сравнивать

Один сервер, один размер 1920×1080, одинаковый масштаб, LAN. Отдельно повторить
2560×1440/4K и ограниченную сеть: RTT 30/80/150 мс, bandwidth 10/30/100 Мбит/с,
потери 0/0.1/1%. Не менять сетевые правила рабочего ПК автоматически.

Сценарии: набор RU/EN, прокрутка длинного документа/веб-страницы, перемещение
окна, видео, простой экрана, несколько вкладок, скрытие/восстановление сеанса.
Сравнить release-сборку с mstsc, xfreerdp3 и Remmina; записать версии, кодеки,
железо, драйверы и серверные параметры. Для xrdp отдельно проверить compositor
и ограничения кодирования на сервере; не отключать его эффекты без сравнения.

Показатели: FPS во время движения, p50/p95 времени от ввода до изменения экрана
(отдельный end-to-end замер), CPU/RAM/GPU, полоса, целостность кадра и чёткость
цветного мелкого текста. RTT не равен задержке ввода. По завершении серии
выставить численные пороги на основе baseline mstsc/xfreerdp, а не выдумывать
проценты ускорения. Функциональные тесты не заменяют benchmark реальных серверов.
